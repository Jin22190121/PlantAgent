## 1. 목적

본 PoC는 한국 원자력발전소의 **최종안전성분석보고서(FSAR)** 한글 PDF를 학습하여 사용자의 질의에 검색·요약·인용 응답을 제공하는 AI Agent를 구현하고, **두 개의 서로 다른 무료 언어모델**을 동일한 RAG 파이프라인 위에서 객관적으로 비교하는 데 목적이 있다.

구체적 목표는 다음 세 가지다.

1. **기술적 실현 가능성 검증**: 한글 원자력 기술문서(스캔 PDF)에 대한 LLM 기반 검색·응답 시스템이 무료 모델만으로 동작 가능한가?
2. **두 시스템의 정량 비교**: 상업 API(Gemini 무료 티어) vs 오픈소스 로컬 모델(EXAONE)의 **품질·속도·비용 트레이드오프**를 데이터로 입증
3. **평가 방법론 정립**: 향후 본 격 시스템 개발에 재사용 가능한 **메트릭·골드셋·자동 리포트** 체계 마련

## 2. 개요

### 2.1 배경

- 원자력발전소 운영허가 신청 시 한수원이 원자력안전위원회에 제출하는 FSAR은 19개 장으로 구성되며, **1장만으로도 100쪽이 넘는다**.
- 운전원 교육·심사 보조·안전 분석 등 현장에서 **방대한 기술문서를 빠르게 검색·요약·인용**할 수요가 크다.
- 한국어 도메인 + 원자력 전문 용어 환경에서 **상용 LLM과 오픈소스 LLM 중 어느 쪽이 적합한가**에 대한 데이터 기반 비교가 부재했다.
- **무료/저비용 모델만으로 PoC가 가능한지** 검증하는 것이 이번 작업의 실용적 동기였다.

### 2.2 시스템 아키텍처

본 PoC는 두 시스템이 **임베딩·청킹·검색·프롬프트·생성 파라미터를 모두 동일하게 공유**하고 **오직 생성 LLM만 다르도록** 격리 설계되었다.

```
스캔 PDF (45MB, 101쪽)
   │
   ▼ Tesseract 한국어 OCR (kor+eng, 300 DPI)
   │
   ▼ RecursiveCharacterTextSplitter (800자/100 overlap)
   │
   ▼ BGE-M3 임베딩 (다국어, 1024 dim) ──┐
   │                                    │  공통 인프라
   ▼ ChromaDB cosine top-k=5           ─┘
   │
   ▼ 공통 프롬프트(qa_ko.txt) + 검색 결과 직렬화
   │
   ├──→ System A: Google Gemini 2.5 Flash Lite (API)
   └──→ System B: LG EXAONE-3.5 2.4B (Ollama 로컬)
   │
   ▼ 메트릭 계산 (Token F1, Recall@k, 지연, 토큰, 비용)
   │
   ▼ 비교 리포트 (JSON / CSV / MD)
```

### 2.3 비교 대상 시스템 요약

| 구분 | System A | System B |
|---|---|---|
| 모델 | **Google Gemini 2.5 Flash Lite** | **LG EXAONE-3.5 2.4B** |
| 제공자 | Google AI Studio | LG AI Research |
| 호출 방식 | REST API (`google-generativeai`) | 로컬 추론 (Ollama) |
| 라이선스 | Google API ToS (무료 티어) | EXAONE AI Model License (비상업 연구) |
| 비용 | 무료 (RPD 1,000 / RPM 15) | 무료 (로컬) |
| 데이터 위치 | 외부 (Google Cloud) | 내부 (Codespace 컨테이너) |

> **모델 선정 변경 이력**: 당초 PoC 설계는 **EXAONE-3.5 7.8B**(한국어 KMMLU 상위, 약 5 GB)였으나, GitHub Codespace 무료 티어의 디스크 32 GB 한계(BGE-M3 임베딩 4.3 GB, Python venv 약 3 GB, 데이터·인덱스 6 GB 등 누적 사용으로 가용 < 2.5 GB)로 인해 **2.4B로 다운그레이드**되었다. 본 결과 해석 시 모델 체급 차(3.3배) 를 감안해야 한다.

## 5. 결과분석 (System A vs System B 비교)

### 5.1 품질 비교 — A 6/6 승

| 차원 | 관찰 | 해석 |
|---|---|---|
| **승부** | A 6승 / B 0승 / 무 0 | 모든 문항에서 A가 동등 이상 |
| **Token F1** | A 0.348 vs B 0.177 (2.0×) | A가 정답 핵심 단어를 더 많이 포함 |
| **Token Recall** | A 0.653 vs B 0.390 (1.7×) | A가 정답에 더 가까운 정보 커버 |
| **Token Precision** | A 0.245 vs B 0.119 | 둘 다 답변이 정답 대비 길어 노이즈 큼 |
| **Keyword 적중률** | A 0.664 vs B 0.458 (1.4×) | A가 핵심 용어 보존 우수 |
| **요약 카테고리** | A 0.299, B **0.000** | B는 컨텍스트 긴 요약에서 크래시 |

**해석**: A는 PDF의 핵심 문장을 정확히 인용하면서 부가 정보를 풍부히 결합한다. B는 단답형(Q01·Q03)에서는 비등하나, 절 번호 추론(Q04 오답)과 긴 컨텍스트 처리(Q05·Q06 크래시)에서 한계가 명확하다. 다만 모델 체급(7.8B → 2.4B 다운그레이드, 3.3배 차)을 감안하면 동일 체급 비교에서는 격차가 줄어들 가능성이 있다.

### 5.2 속도 비교 — A 118~183× 우세

| 차원 | A (Gemini) | B (EXAONE 2.4B) | 비율 |
|---|---|---|---|
| 평균 지연 | 1.35초 | **160초** (2분 40초) | 118× |
| p95 지연 | 1.49초 | **273초** (4분 33초) | 183× |

**해석**: B의 지연은 CPU 추론 + 디스크 압박(가용 700 MB) + 메모리 스와핑이 복합 작용한 결과. 동일 모델이라도 GPU 환경에서는 토큰당 시간이 10~30배 빨라질 수 있어 결과가 달라질 수 있다. 그러나 **대화형 UI 시나리오에서 4분 응답은 실용성 불가** — A만 실배포 가능.

| 답변 길이 | 풍부·부가 정보 결합 (평균 74 토큰) | 간결, 일부 짧음 (평균 42 토큰) |
| 한국어 자연스러움 | 양호 | 양호 |
| 형식 준수 | 프롬프트 인용 포맷 충실 | 인용 포맷에 변형 발생 |
| 위계 추론 | 우수 (Q04 1.1절 정답) | 한계 (Q04 1.2로 오답) |
| 긴 컨텍스트 안정성 | 안정 | **불안정 (요약 문항 크래시)** |

### 5.6 통합 판정

> **본 6문항 PoC 결과에 한정하면, System A (Gemini 2.5 Flash Lite)가 품질·속도·안정성 모든 차원에서 우세하다.**
>
> 그러나 다음 두 가지가 결과 해석에 결정적이다:
> 1. **모델 체급 비대칭** — 당초 EXAONE 7.8B가 Codespace 디스크 한계로 2.4B로 다운그레이드되어 공정 비교 어려움. **EXAONE 7.8B를 GPU 환경에서 재평가하면 격차가 상당 부분 좁혀질 가능성**이 있다.
> 2. **공통 검색 한계** — 두 시스템 모두 Retrieval Recall@k = 0.5에서 막혔다. LLM이 아니라 **검색 단계 개선이 다음 마일스톤**이다.

### 5.7 시나리오별 권장

| 시나리오 | 권장 시스템 |
|---|---|
| 대화형 보조 UI (저지연 필수) | **System A** (Gemini) |
| 인터넷 격리·온프레미스 필수 | System B (EXAONE) — GPU 필수 |
| 대량 배치 처리 (수만 건/일) | System B — GPU 환경 전제 |
| 한국 원자력 도메인 정확성 우선 | **재평가 필요** (현 결과는 모델 체급 차) |
| PoC·시제품 단계 | **System A** (즉시 시작, 무료) |

### 5.8 후속 과제 (우선순위 순)

| 우선 | 과제 | 기대 효과 |
|---|---|---|
| 1 | EXAONE 7.8B를 GPU 환경(Colab T4 / RunPod)에서 재평가 | 모델 체급 공정 비교 |
| 2 | 골드셋 20+ 문항으로 확장 (PDF 다른 페이지 캡쳐 보강) | 통계적 신뢰도 향상 |
| 3 | Hybrid 검색 (BM25 + Dense) + Reranker 도입 | Retrieval Recall@k 향상 → 양 시스템 공동 이득 |
| 4 | OCR 품질 개선 (600 DPI, 노이즈 제거 전처리) | 청크 텍스트 품질 ↑, 인용 노이즈 ↓ |
| 5 | LLM-as-Judge 평가 보완 | Token F1의 형식적 한계 보정 (의미 기반 점수) |
| 6 | 카테고리 균형 조정 (사실/위치/요약/비교/추론 각 5문항) | 시나리오별 강·약 정확 파악 |
| 7 | 운영 비용 모델링 (GPU 시간당 vs Gemini RPD 초과 단가) | 실 배포 의사결정 근거 |
